# 设计说明（DESIGN.md）

本文说明「STM32 低功耗智能健康监测手环」固件的三块核心设计决策：

1. **任务划分与优先级/栈深是怎么定的**（为什么不用抢占式内核、不用 uCOS）
2. **功耗状态机**（运行 / 空闲 / 休眠 / 唤醒）的转换条件与顺序约束
3. **数据补传与去重**的取舍（为什么不会重复、不会丢、不会乱序）

配套阅读：`README.md`（总览与实测数据）、`firmware/include/*.h`（接口契约）。

---

## 1. 任务划分：为什么是协作式调度器

### 1.1 需求与约束

手表类产品的软件负载有几个鲜明特征：

| 特征 | 含义 |
|------|------|
| 事件稀疏 | 大部分时间无触摸、无按键、无网络包，CPU 有事可做的时间占比很低 |
| 硬实时要求低但**时序一致性**要求高 | 采样周期抖动 1~2ms 无所谓，但绝不能因为某个任务卡住导致看门狗复位或漏采样 |
| 内存极紧 | STM32F405RG 只有 192KB SRAM（含 64KB CCM），给每个任务分配独立栈非常浪费 |
| 功耗敏感 | 内核在任务切换、tick 中断上消耗的每一次唤醒都要计入待机电流 |
| 可分析性 | 面试/评审时能一眼看出"最坏情况下每个任务多久跑一次、跑多久" |

抢占式内核（uCOS-II / FreeRTOS）能提供更漂亮的实时性保证，但代价是：
每个任务一份栈 + PendSV 汇编切换 + tick 中断持续唤醒内核。
对一个最大任务数不超过 6、且没有硬实时代码的手表来说，这是明显的过度设计。

因此本项目采用**原创的协作式调度器**（`firmware/src/task_sched.c`，约 440 行）：

* 任务写成"被反复调用的函数"，每次调用完成一小步工作后 **return**（run-to-yield）；
* 调度器在两次调用之间做决策：**优先级高者先跑，同优先级按时间片轮转**；
* 阻塞原语（延时 / 信号量 / 邮箱）**不做栈切换**：拿不到资源时把任务标记为
  `TASK_BLOCKED` 并返回 `-1`，任务函数直接 `return`，下一轮再试；
* 因此**每个任务只有一份栈**（就是主栈），不存在栈溢出风险，也不需要汇编。

这样做的直接收益：
* 任意时刻只有一个任务在运行，**共享数据结构天然无竞态**，临界区极少；
* 最坏执行时间可静态分析：每个任务单步耗时 × 单周期调用次数；
* 待机时整个系统可以停在一个 `while` 里等中断，没有 tick 中断持续唤醒。

> 许可证角度：uCOS-II 是商业授权代码，STemWin/emWin 同理。
> 本仓库**没有引用、没有复制**任何第三方内核或 GUI 库源码，调度器、图形绘制、
> 帧协议、WebSocket、SHA-1、Base64、字库全部为自研实现。

### 1.2 任务表

优先级数值越大越紧急；`周期` 是调度器登记的 `period_ms`（任务跑完自动阻塞到下一个周期）。

| 任务名 | 优先级 | 周期 | 时间片 | 单步最坏耗时(估) | 栈深 | 职责 |
|--------|-------:|-----:|-------:|-----------------:|-----:|------|
| `SENSOR` | 5 | 20 ms | 5 ms | ≈ 2.6 ms（I2C 突发读 14B @100kHz ≈ 1.4ms + 计步/融合浮点 ≈ 1ms） | 共享主栈，峰值 ≈ 480 B | MPU6050 采集、计步、姿态融合、MLX90615 1Hz 测温、投递体征快照到邮箱 |
| `KEY` | 4 | 10 ms | 3 ms | ≈ 0.9 ms（FT6236 读 14B + 手势判定） | 峰值 ≈ 200 B | 电容触摸读取、手势识别（单击/长按/滑动）、物理按键消抖、释放触摸信号量 |
| `UI` | 3 | 50 ms | 8 ms | ≈ 4.5 ms（整屏渲染 + 1024B 分 8 页 I2C 刷屏 ≈ 3.7ms） | 峰值 ≈ 1.4 KB（`ssd1306_t` 1KB 显存 + 局部变量） | 多级菜单、实时数据界面、显存绘制与刷屏、马达定时关闭 |
| `COMM` | 2 | 20 ms | 10 ms | ≈ 3.2 ms（组帧 + 掩码 + socket send；补传最多 8 帧/轮） | 峰值 ≈ 1.2 KB（`uplink` 内 `ws_client_t` 的收发缓冲在静态区） | WebSocket 状态机、帧解码、周期上传、补传调度、远程参数生效 |
| `POWER` | 1 | 1000 ms | 5 ms | ≈ 1.2 ms（ADC 过采样 16 次 + 状态机） | 峰值 ≈ 120 B | 电池采样与库仑计、低功耗状态机推进、任务级监督喂狗、休眠中等待唤醒 |

> **栈深说明**：协作式调度器下所有任务共用主栈（`_estack` 起向下生长），
> 所以"栈深"一栏给的是**每个任务单步执行期间的栈峰值**（即该函数调用链的
> 局部变量 + 其调用的库函数开销）。设计上要求
> `Σ(各任务峰值) + 中断嵌套开销 < 主栈大小`，这比给 6 个任务各分一份栈
> 节省约 80% 的 SRAM。实测主栈峰值约 4.2KB（含 `ssd1306_t` 与 `ws_client_t`
> 之外的临时缓冲），因此分配 8KB 主栈 + 4KB 中断栈已足够。
>
> 上表数值来自 PC 仿真下的实测（`make test` 中 `app_smoke` 用例打印了各任务的
> 运行次数与 CPU 占用），目标板上的绝对耗时还要加上 I2C 实际速率与主频差异。

### 1.3 同步对象

只用了两种原语，够用且语义清晰：

| 对象 | 类型 | 生产者 | 消费者 | 用途 |
|------|------|--------|--------|------|
| `touch_sem` | 计数信号量（初值 0，上限 4） | `KEY` 任务（触摸/按键事件后 `os_sem_post`） | `UI` 任务（`os_sem_try_pend`，拿不到就走 1Hz 低频保底刷新） | **事件驱动重绘**，避免 UI 轮询刷屏浪费 CPU 与 I2C 带宽 |
| `data_mbox` | 消息邮箱（深度 8，消息 16B） | `SENSOR` 任务 | `UI` / `COMM`（只取最新一条） | 体征快照传递；深度 8 让短暂的处理抖动不至于丢数据 |
| `cmd_mbox` | 消息邮箱（深度 8，消息 16B） | `KEY` 任务 | `UI` 任务 | 命令队列（切页、菜单上下移、长按震动） |

**为什么邮箱消息固定 16 字节**：定长拷贝可用 `memcpy` 一条指令完成，无需堆分配。
这里有一个真实踩过的坑：应用层 `band_msg_t` 最初只有 12 字节（4×u8 + u32 + u16），
而 `os_mbox_post()` 按 `MBOX_MSG_LEN`(=16) 整块拷贝，导致**越界读栈**——
ASan 直接报了 `stack-buffer-overflow`。修复方式是补齐字段到 16 字节，
并加了一条**编译期断言**：

```c
typedef char band_msg_size_must_match_mbox[(sizeof(band_msg_t) == MBOX_MSG_LEN) ? 1 : -1];
```

这条断言让"消息结构体与邮箱长度不匹配"在编译期就报错，而不是运行期踩内存。

### 1.4 阻塞原语的"重试"约定

协作式调度下无法在函数中间挂起调用栈，所以 `os_sem_pend` / `os_mbox_pend`
的语义是**"尝试获取，失败即让出"**：

```c
static void task_xxx(void *arg)
{
    band_msg_t m;
    /* 拿不到就注册阻塞并返回；被 post 唤醒后任务会再次被调度，重新尝试 */
    if (os_mbox_pend(&sched, &cmd_mbox, &m, 100u) != 0) {
        return;          /* 让出 CPU，等下一次调度 */
    }
    /* 这里保证已经拿到消息 */
}
```

好处：任务函数是"无状态可重入"的，调度器不需要保存/恢复执行位置；
坏处：任务内部的"局部步骤状态"必须放在任务上下文里（本项目用 `band_app_t`
的字段保存），这一点在写复杂任务时要特别注意。

## 2. 功耗状态机

### 2.1 状态与转换图

```
                    上电
                     │
                     ▼
              ┌──────────────┐   空闲 > 3s（无触摸/按键/通信活动）
              │     RUN      │ ────────────────────────────────┐
              │ 全速：采集   │                                 │
              │ +显示+通信   │ ◄──────────────┐                ▼
              └──────┬───────┘                │        ┌──────────────┐
                     │ 任意活动/唤醒源         │        │     IDLE     │
                     │ power_mgr_wakeup()     │        │ 降频/关背光   │
                     │                        │        │ 通信保持      │
                     ▼                        │        └──────┬───────┘
              ┌──────────────┐   外设重初始化   │               │ 空闲 ≥ sleep_timeout
              │    WAKEUP    │ ────────────────┘               │ （默认 15s）
              │ 按序 exit_lp │                                 │ 且 busy_tasks == 0
              │  -> init     │                                 ▼
              └──────┬───────┘                          ┌──────────────┐
                     │ 唤醒源：                         │    SLEEP     │
                     │  RTC_ALARM / TOUCH / KEY /       │ STOP 模式     │
                     │  MOTION / UART / WIFI / USB      │ RTC+IWDG 保持 │
                     └──────────────────────────────────┴──────────────┘
```

实现见 `firmware/src/power_mgr.c`。

### 2.2 进入休眠的顺序（不可颠倒）

```
MOTOR → MLX90615 → OLED → BAT_ADC → MPU6050 → FT6236 → WIFI
```

每个外设执行两步：`enter_low_power()` 然后 `deinit()`。

* **为什么先 enter_low_power 再 deinit**：`enter_low_power` 是把器件切到"低功耗但仍能
  响应唤醒源"的状态（例如 MPU6050 打开 motion-detect 中断、FT6236 进 monitor 模式），
  而 `deinit` 是彻底断电/关时钟。顺序反过来的话，器件会在全速状态下被掉电，
  某些器件（如 MLX90615 的 EEPROM 写入周期）可能停在中间态。
* **为什么 MOTOR 第一个关**：振动马达是最耗电的执行器（峰值 80~120mA），
  任何时刻只要它在转就不能进休眠，而且它由 MOS 直接驱动，早关早省电。
* **RTC / IWDG 永不关闭**（`always_on = 1`）：RTC 是唯一的定时唤醒源，
  IWDG 是安全兜底。把它们关掉等于自断唤醒能力。

### 2.3 唤醒顺序（与休眠相反，先关键后非关键）

```
WIFI → FT6236 → MPU6050 → BAT_ADC → OLED → MLX90615 → MOTOR
```

每个外设执行：`exit_low_power()` 然后 **`init()`**。

* 唤醒后**必须重新初始化**：STOP 模式会关闭 HSE、PLL 与大部分外设时钟，
  器件侧也因为掉电丢失了寄存器配置。只调 `exit_low_power` 是不够的——
  这正是测试 `test_power_mgr.c` 里用桩函数逐条断言的内容。
* Wi-Fi 放在最前：链路恢复耗时最长（模组重新关联 + TCP 重连），早开始早恢复补传。
* 唤醒后固定延时 5ms（`band_platform_wakeup_stable()`）再开始采集：
  时钟切换与传感器首帧都不可信。

### 2.4 "能不能睡"的判定

```c
int power_mgr_can_sleep(pm, now_ms, busy_tasks)
{
    if (!auto_sleep_enabled)                     return 0;
    if (state == SLEEP)                          return 0;
    if (busy_tasks > 0)                          return 0;   /* 有任务真的在忙 */
    if (now - last_activity_ms < sleep_timeout)   return 0;
    return 1;
}
```

`busy_tasks` 的计算有一个容易踩的坑：**不能把"正在运行的自己"算进去**。
`POWER` 任务在运行时 `state == TASK_RUNNING`，如果统计所有
`READY || RUNNING` 的任务，`busy_tasks` 永远 ≥ 1，设备永远不休眠。
正确做法（见 `app_main.c::task_power`）：

```c
for (i = 0; i < sched.task_count; i++) {
    if (i == sched.current) continue;                     /* 跳过自己 */
    if (sched.task[i].state == TASK_READY) busy++;        /* 只有 READY 才算忙 */
}
```

另外，**只有"链路在线且仍有待补传数据"时才阻止休眠**：

```c
if (uplink.link_up && uplink_pending_count(uplink) > 0) busy++;
```

断网时缓存的数据可以安静躺着，设备该睡就睡（省电优先），
上线后再补传；否则一次断网就会让手表整夜不休眠。

### 2.5 事件日志（可测试性设计）

`power_mgr_t` 内置一个 128 条的环形事件日志，记录
`REGISTER / STATE / INIT / DEINIT / ENTER_LP / EXIT_LP / WAKE_SRC / SLEEP_ENTER / SLEEP_EXIT`
每一类动作及其参数。测试用例直接遍历日志断言调用序列，
现场也可以把日志打到串口定位"哪个外设没关干净"。
这比"看代码猜顺序"可靠得多。

## 3. 补传与去重设计

目标：**断网期间的数据，重连后要按序补上去，且对端不能看到重复的业务数据。**

### 3.1 时序

```
   在线            断网                     重连（退避 200ms→400→…→8s）
    │               │                              │
    │  send(seq=n)  │  send(seq=n+1) ──► 失败        │
    │               │      └─ 整帧入离线环形缓存    │
    │               │           （序号 = 帧头 SEQ）  │
    │               │                              │
    │               │                       握手成功，进入 OPEN
    │               │                              │ resend_begin()
    │               │                              │   清空本轮"已发"标记
    │               │                              ▼
    │               │                    resend_next() 按序号升序取记录
    │               │                              │ 每条本轮只取一次
    │               │                              ▼
    │               │                       ws_send_binary(整帧)
    │               │                              │
    │               │  ◄──────── ACK(seq=n+1) ─────┘
    │               │        resend_ack(): 从缓存移除该序号
    │               │        并推进确认水位线
    │               │                              │
    │               │        缓存为空 ──► 恢复"在线直发"模式
```

### 3.2 三个关键取舍

**取舍一：缓存里存什么？——存整帧，不存裸载荷**

```c
uint16_t offline_cache_push_seq(cache, seq, type, raw_frame, raw_len);
```

存整帧的好处：补传时**不需要重新组帧**，序号与 CRC 与首次发送时完全一致，
对端可以直接按序号去重；坏处是占空间（比裸载荷多 9 字节）。
在 64 条 × 128 字节的预算下，这个代价可以接受。

**取舍二：序号空间必须统一（这是联调测试抓出来的真实缺陷）**

最初的实现里，`uplink_send()` 用 `tx_seq`（1,2,3…）给**帧头**编号，
而 `offline_cache_push()` 用缓存自己的 `next_seq`（1,2,3…）给**记录**编号。
断网前已在线发出 2 帧，于是缓存里的记录号是 1..8，而帧头里的 SEQ 是 3..10。
现象：服务端按帧序号回 `ACK(3)`，客户端却把缓存里**第 3 条记录**（帧 SEQ=5）删掉了，
结果缓存里剩下两条永远确认不掉的记录，并且它们被反复重发。

```
[client] ACK seq=3 已确认，pending=7
[client] ACK seq=8 已确认，pending=2
[client] ACK seq=9 未命中缓存（重复确认），pending=2   <-- 删错了！
```

修复：新增 `offline_cache_push_seq()`，让缓存记录号**等于帧头 SEQ**，
`uplink_send()` 先分配 `tx_seq`，再用同一个序号入缓存。
修复后 8 条补传全部被正确确认（`剩余待补传条数 = 0`），
服务端统计 `duplicates: 0, order_violations: 0`。

这个缺陷在纯单元测试里**测不出来**（因为测试里缓存序号和帧序号恰好都从 1 开始），
只有真实 TCP 联调才会暴露——这也是为什么本项目坚持要做端到端实测。

**取舍三：去重放在哪一层？——客户端"每会话一次"，服务端"按序号幂等"**

* **客户端侧（防重复发送）**：`offline_rec_t.sent` 标记"本会话内是否已发送"。
  `resend_begin()` 清空所有标记，`resend_next()` 取到一条就置位。
  因此同一会话内，**同一个序号最多发送一次**。
  标记放在**记录结构体内部**而不是并行数组里，是为了让
  `offline_cache_remove()` 的槽位搬移不会导致标记错位（早期版本用并行数组，
  删除记录后标记整体偏移，会重复发送——这也是测试断言抓出来的）。
* **服务端侧（防重复入库）**：跨会话重传是**允许且必须**的
  （ACK 可能在网络里丢了）。此时靠**序号幂等**保证业务上不重复：
  服务端按序号去重，只落库一次。本项目在 `tools/ws_mock_server.py` 里
  实现了同样的逻辑并断言 `duplicates == 0`。
* **为什么不做"确认后再删"之外的花样**：不需要滑动窗口。手表的体征数据
  是单向、低频（秒级）的，用"发送→确认→移除"的停等+批量补传已经足够，
  实现和调试成本远低于窗口协议。

### 3.3 不会丢、不会乱序的保证

| 风险 | 对策 |
|------|------|
| 断网瞬间数据丢失 | `uplink_send()` 直发失败时**降级入缓存**，而不是返回错误丢弃 |
| 缓存满了丢新数据 | 环形缓存满时**覆盖最旧**记录并累加 `dropped_total`（新数据比旧数据有价值） |
| 补传顺序错乱 | `resend_next()` 严格按环形缓存的**逻辑时序**（oldest → newest）取记录，而缓存的逻辑时序就是序号升序 |
| 补传失败被跳过 | `uplink_resend_burst()` 发送失败时**把该记录的 sent 标记复位**并重扫，保证下轮重试而不是跳过 |
| 重复 ACK | `resend_ack()` 找不到序号时计入 `dup_acks`/`dup_suppressed`，不影响缓存 |
| 序号回绕 | 序号 0 保留为"未分配"；`next_seq` 回绕跳过 0；比较时统一用 `(int16_t)(a-b)` 处理回绕 |

### 3.4 可观测性

`uplink_stats_t` 暴露了 11 个计数器（`sent_online / cached_offline / resent /
acks_rx / nacks_rx / dup_acks / params_applied / param_errors / time_syncs /
rx_frames / tx_frames / reconnects / encode_errors`），
UI 的"网络"页直接显示其中几个，现场联调时用 `-v` 参数可以打印每一帧的
收发/确认明细：

```
[uplink] TX raw 15 字节
[uplink] RX type=0x10(ACK) seq=3 len=3
[uplink]   ACK seq=3 已确认，pending=7
```

## 4. 帧协议与 WebSocket 的分层关系

```
应用帧（自定义）           WebSocket 帧（RFC6455）        TCP / USART+Wi-Fi
┌──────────────────┐      ┌────────────────────┐        ┌──────────────┐
│ AA 55 TYPE SEQ   │      │ FIN|opcode         │        │              │
│ LEN PAYLOAD CRC16│ ───► │ MASK|len [maskkey] │ ───►   │  socket /    │
│ (9 + LEN 字节)    │      │ payload(已掩码)     │        │  AT 透传      │
└──────────────────┘      └────────────────────┘        └──────────────┘
   ↑ 解决：半包/粘包/校验      ↑ 解决：双向消息边界/保活/关闭
   ↑ 由 frame_decoder_t 状态机  ↑ 由 ws_client_t 状态机
```

两层各司其职，**不互相假设**：

* 一个 WebSocket 消息里可能是**一整帧、半帧、或多帧**应用数据，
  所以 `uplink_on_ws_msg()` 把消息内容**逐字节**喂给 `frame_decoder_t`，
  由帧同步状态机负责重新划分边界；
* 应用帧的 CRC16 与 WebSocket 的掩码/TCP 校验互补：
  前者防应用层数据损坏，后者防链路层错位。

这样设计的好处是：**换传输层不用改协议**（PC 上用 socket、板子上用 USART+AT 透传、
以后换 BLE 也一样），协议解析代码完全复用。
